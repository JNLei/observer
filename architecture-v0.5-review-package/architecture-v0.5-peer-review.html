AI Native Observability Architecture Spec v0.5 Peer Review

Verdict: v0.5 is a coherent conceptual baseline for the scoped prototype. No P0 defect or demonstrated irreconcilable contradiction was found. The review retains 14 distinct conditional risks: one P1 clarification, ten P2 gates and three P3 clarifications. These identify how plausible implementations or tests could miss intended guarantees; they are not 14 observed software bugs or reasons to restart the architecture.

The most consequential clarifications concern derived-data confidentiality, authenticated source attribution, accounting for work after cancellation, and stateful metric replay. Tighten those contracts and tests before the affected paths are enabled. Keep Rust as a preference pending the already-required production-shaped comparison; this review supplies no measured language verdict.

Method and independence

Three separate reviewer instances ran in parallel inside this chat. Each started without conversation history, read the complete Markdown and DOCX content, and independently searched current external official/primary sources. They did not see each other’s findings during the independent pass. Each saved a separate report before cross-review. All used the same underlying model family; these are independent execution/context passes, not three different model families or independent human experts. Shared model limitations can produce correlated blind spots. Agreement is a useful signal, not proof.

Reviewer 1 covered telemetry, backpressure, recovery, correctness, Rust/Go and resource isolation. Reviewer 2 covered security, authorization, privacy, trust boundaries and IaC/headless operations. Reviewer 3 covered GenAI semantics, agent/evaluation records, evidence and lifecycle consistency. Reference-conversation text was used only to locate files, not supplied to the reviewers as technical authority.

Each reviewer retained existing protections and explicitly differentiated unresolved choices from defects. External technical claims rely on official documentation/repositories or original research. Prioritized findings and concrete changes

P1 S01 Carry confidentiality into derived artifacts

Independent origin: R2-01 + R3-01 · Classification: conditional risk / implementation or acceptance gate

Source locations. §17 A6–A7, MD 842–856; §22.1, MD 1016–1018. DOCX P0941–P0948 and P1124–P1125; rendered pp. 21–22, 27.

Spec anchor. “Access to a trace does not automatically imply access to every protected payload.”

Counterexample and impact. A permitted worker reads a restricted payload and copies a sensitive fact into an ordinary incident report. A less privileged user can read the report while its source handle correctly returns DENIED. Shared authorization at each endpoint has not prevented disclosure through the new object.

Proposed fix. Require derived-disclosure policy for reports, evaluator explanations, datasets, caches, search snippets, worker telemetry and exports. Preserve sensitivity and dependency lineage; inherit restrictions or apply explicit authorized redaction/declassification. Revalidate source-dependent reads after relevant permission changes; independently authorized declassified publications follow their declared policy. Safe aggregate disclosure may deliberately differ from source ACLs, but must be a documented policy decision.

Acceptance evidence. Two users share trace/report access but only one can read a canary-bearing payload. Generate derivatives, revoke access, rebuild, cache and export. No restricted canary may reach the other user unless an explicit declassification test authorizes that disclosure.

Calibration and gate. A7 already governs processing, retrieval and classification. This is a testable composition clarification of that invariant, not proof that v0.5 permits disclosure. Gate before serving sensitive persisted derivatives.

Official or primary support. AWS data and retrieval security · OPA data filtering. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S02 Separate submitted identities from authenticated source attribution

Independent origin: R2-02 + R3-04 · Classification: conditional risk / implementation or acceptance gate

Source locations. §7.1/7.3, MD 330–336 and 370; A1, MD 798–804; D3, MD 914; I5, MD 995. DOCX P0372–P0375, P0392, P0919–P0922, P1019–P1021, P1108–P1110; pp. 9, 20, 23, 26.

Spec anchor. “whether it is authoritative or heuristic”

Counterexample and impact. A compromised tenant writer supplies another service’s name and copied trace/span/session IDs. Exact joins and immutable storage can then turn an attributed submission into apparently trusted service history or allow a conflicting copy to replace a more trusted observation. A valid ingest credential authenticates its holder, not every claim in its payload.

Proposed fix. Retain original trace IDs and legitimate distributed links, while recording server-observed ingest principal/channel and a separate attribution/trust basis. Constrain source/resource claims where service isolation is promised. Tenant-scope storage/authorization keys, preserve cross-source correlation, and qualify observation collision/deduplication ownership only where necessary to avoid replacement. Define completion and revision authority separately. ID knowledge cannot grant membership or override rights.

Acceptance evidence. With service A’s credential, submit B’s names, copied IDs, parent links and completion records. Reject or retain them as A-attributed claims without altering B’s trusted state or ACLs. Repeat across tenants and after rebuild; legitimate multi-service tracing must still work.

Calibration and gate. Initial ratings differed: R2 P1, R3 P2. Cross-review and synthesis use P2 for this specification gap; a demonstrated breach of claimed service-level writer isolation or protected completion authority would warrant P1. Do not require per-event signatures or prefix IDs in a way that destroys valid tracing.

Official or primary support. W3C Trace Context security considerations. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S03 Keep cancelled work charged until it actually stops

Independent origin: R1-01 · Classification: conditional risk / implementation or acceptance gate

Source locations. §22.1, MD 1016; §22.5, MD 1066; §23.2, MD 1095. DOCX P1124, P1175–P1176, P1209; pp. 27, 29–30.

Spec anchor. “Enforce time/result/byte/cost/concurrency budgets, cancellation, deadlines and pagination.”

Counterexample and impact. A timed-out query releases its concurrency permit, but its CPU task or remote scan continues for a minute. Repeating one-second timeouts creates many running scans while the gateway appears within its budget. Tokio blocking tasks can continue after cancellation; closing a client connection does not guarantee backend work stops.

Proposed fix. Separate cancellation requested, termination confirmed and bounded outstanding noncancellable work. Retain resource charges until actual completion, or use a separately bounded orphan-work budget. Propagate deadlines, bound fan-out and blocking queues, and provide cooperative cancellation or isolated execution for noncooperative work.

Acceptance evidence. Repeatedly cancel an intentionally noncooperative task and a scan that ignores disconnect. Measure actual outstanding work and cancellation-to-stop delay; verify peer ingest/alert SLOs, not only fast timeout responses.

Calibration and gate. Original R1 rating P1 was lowered to P2 because bounded execution/isolation already imply the intended outcome and no unsafe implementation was supplied. Add this concrete accounting test to the production prototype; no particular executor is prescribed.

Official or primary support. Tokio spawn_blocking cancellation and CPU limits · gRPC cancellation responsibilities. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S04 Recover stateful metric semantics as well as queued records

Independent origin: R1-02 · Classification: conditional risk / implementation or acceptance gate

Source locations. §7.2, MD 354; §21, MD 991–1006; §23.2–23.3, MD 1083–1108. DOCX P0384, P1096–P1119, P1190–P1228; pp. 9, 26–27, 29–30.

Spec anchor. “Preserve metric resolution, aggregation window, rollup/downsampling and counter semantics.”

Counterexample and impact. Two replay workers independently convert one OTLP delta stream to cumulative values under the same series identity. Every input can be durable and accounted for while output counters, rates and histogram counts are wrong. Restart, resharding and live/backlog routing can lose or split accumulator state.

Proposed fix. For each stateful adapter/processor, define stream identity, logical writer, partition ownership, reset epoch, state recovery and failover behavior. Preserve both metric timestamps. Choose native delta handling or an explicitly semantics-preserving conversion strategy; stateless adapters need no unnecessary durable accumulator.

Acceptance evidence. Replay a known delta/histogram stream through duplicates, reordered lanes, crashes and ownership transfer. Compare values and derived rates with a golden result, allowing only explicitly declared reset/disposition behavior.

Calibration and gate. Original R1 P1 was lowered to P2 at specification stage; no converter design was selected. Applicability is conditional on enabling a stateful transformation. The spec already requires counter semantics and ordering compatibility. This refines the adapter correctness gate; it does not claim parallel recovery is always invalid.

Official or primary support. OTel metric single-writer and temporality · Collector delta-to-cumulative processor. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P3 S05 Declare the fate of GenAI log events in the AI model

Independent origin: R3-02 · Classification: conditional risk / implementation or acceptance gate

Source locations. A1, MD 798–802; §21, MD 991–998, especially 998. DOCX P0919–P0921, P1097–P1115; pp. 20, 26.

Spec anchor. “Canonical traces additionally feed asynchronous AI projections”

Counterexample and impact. Supported instrumentation sends content only as GenAI LogRecords; an external evaluation.result uses response ID without a span ID. Raw logs store both, but a trace-only projector and separate evaluation-submission API never associate them with AI observations or scores. Successful OTLP intake then overstates interoperability.

Proposed fix. For every selected convention/version/mode, declare whether an event is linked/promoted, available only as raw evidence with an explicit capability limitation, or unsupported. Support authorized cross-signal and late/orphan association where claimed. Preserve EventName and trace/span/response identifiers without inventing missing spans or independent truth.

Acceptance evidence. Exercise content on spans, event-only, both, and evaluation events with/without retained spans. Reorder, duplicate, restart and rebuild. Supported associations must survive without double counting; unsupported modes must have visible limitations.

Calibration and gate. The spec does not forbid log inputs, and versions/mappings are expressly deferred. Original R3 P2 was lowered to P3 because this is a compatibility-matrix completeness test, not a proven span-only prohibition. A release falsely claiming such support would have a P2 implementation defect. Gate before claiming those modes are supported.

Official or primary support. Pinned official GenAI event conventions · OTel log/event data model. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S06 Identify the resolved evidence used by each evaluation attempt

Independent origin: R3-03 · Classification: conditional risk / implementation or acceptance gate

Source locations. §8.5, MD 467–473; §19.2–19.3, MD 927–935; §22.4, MD 1047. DOCX P0482–P0485, P1036–P1040, P1157; pp. 11, 24, 28.

Spec anchor. “results may change due to late data, retention, reindexing, and rollups”

Counterexample and impact. Attempt A evaluates target v1 using S1/S2, then crashes. Late S3 arrives; retry B evaluates the same target/version using S1/S2/S3. Idempotent publication chooses a result, but a target ID and mutable query handle cannot establish which input set the published judgment actually used.

Proposed fix. Record the winning attempt, declared reproducibility mode, and permitted bounded judge-input identity/payload or digest with resolution time, coverage and source/configuration lineage. A detailed manifest is an option, not mandatory enumeration of every contributing source record. Changed inputs need a new input revision or an explicit statement that attempts evaluated different sets. An immutable snapshot is one option; do not require global serializability or retain forbidden content.

Acceptance evidence. Pause after resolution, insert late telemetry/change context, crash and retry across multiple stores. Each published result must attribute the actual winning attempt and declared input identity/limits; equal query fingerprints must not imply equal evidence. Explicitly mark mutable or unretained inputs; allowed deletion may make later reproduction impossible.

Calibration and gate. Mutable references, snapshots and late revisions are already recognized. This is a narrower lineage invariant within the existing lifecycle gate. It belongs before enabling this path, even if a public API freeze is later.

Official or primary support. Langfuse judge execution and inputs · OTel schema interpretation. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S07 Keep corrected quality views distinct from cumulative event metrics

Independent origin: R3-05 · Classification: conditional risk / implementation or acceptance gate

Source locations. TEST-028, MD 651; A5, MD 836–838; D5–D6, MD 916–917; §22.4, MD 1049. DOCX P0805–P0807, P0938–P0939, P1025–P1030, P1158; pp. 17, 21, 24, 28.

Spec anchor. “aggregate excludes superseded results under declared rules”

Counterexample and impact. A passing judgment increments a success counter, then is corrected to failure. Canonical current-result analytics now has zero successes, but the monotonic counter cannot remove its old increment. Counting the failure too changes the population to judgment events; replay/rebuild can create more duplicates or resets.

Proposed fix. Define separate event/attempt counts and current-judgment quality views. Use a representation that can reflect correction/recomputation for the latter. Declare target-time versus publication-time windows, supersession, as-of/revision semantics and one logical exporter writer, with bounded labels.

Acceptance evidence. Run pass→fail→correction, late results, two exporter replicas, restart, rebuild and retention expiry. Every export claiming current-view semantics must agree with canonical analytics for the same population/window/as-of.

Calibration and gate. No counter is required by v0.5; formulas and supersession are deferred. This is an export compatibility test, not a contradiction. A gauge can correct present state but cannot retroactively repair previously scraped historical samples. Keep historical analytical truth and current/publication-time exports distinct where the backend requires it.

Official or primary support. Prometheus metric types · OTel single writer. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S08 Validate judges before calling their scores accuracy

Independent origin: R3-06 · Classification: conditional risk / implementation or acceptance gate

Source locations. A4–A5, MD 828 and 834–838; §22.4, MD 1047–1049. DOCX P0934, P0937–P0939, P1157–P1158; pp. 21, 28.

Spec anchor. “diagnosis accuracy, groundedness, evaluation pass rates”

Counterexample and impact. A wrong answer includes instructions to award a maximum score, or verbosity biases the judge. The judge completes successfully, permissions hold, and versions/denominators are correct, yet the quality metric is invalid. Execution health and provenance do not establish measurement validity.

Proposed fix. Add task-specific evaluator validation: independently labeled or deterministic cases, agreement/error analysis, abstention, repeatability and adversarial answer-content tests. Associate validation status and limits with evaluator versions. Exploratory scores can be recorded before validation, but must not silently become verified accuracy or trusted promotion/alert evidence.

Acceptance evidence. Include correct/incorrect diagnoses, unsupported causal claims, missing evidence, irrelevant verbosity and scoring instructions. A judge-version change must meet declared task criteria before equivalent use; retain validation data/version and limits.

Calibration and gate. Primary studies establish possible judge biases/attacks, not an attack rate for a future selected model. No universal accuracy threshold, mandatory ensemble or ban on model judges follows.

Official or primary support. Raina et al. EMNLP 2024 adversarial judge study · Zheng et al. MT-Bench judge study. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S09 Constrain native-query capabilities, not only returned rows

Independent origin: R2-03 · Classification: conditional risk / implementation or acceptance gate

Source locations. §8.1, MD 380–384; §9.1, MD 489; §22.1, MD 1016; §22.5, MD 1057. DOCX P0397–P0399, P0493, P1124, P1162; pp. 10, 12, 27–28.

Spec anchor. “Validate backend-native escape hatches with the same controls.”

Counterexample and impact. A future adapter exposes SELECT syntax that can read a URL or file under its backend credential. Row/time/result limits all hold, yet a server-side request reaches an internal or unapproved destination. Query permission has become network capability.

Proposed fix. Declare each adapter’s data-only query subset and least-privilege backend role. Gate URL/file/network/UDF/executable and settings/catalog capabilities separately, with actual egress enforcement. Disable native features that cannot safely be confined.

Acceptance evidence. Use instrumented internal/external destinations and files; attempt functions, aliases, subqueries, settings and redirects. No unauthorized request/read may occur, including queries that ultimately return errors.

Calibration and gate. No engine is selected. ClickHouse is an example: its current url() permissions and readonly=1 restrictions can block this path. This is a conditional adapter gate, not a demonstrated default vulnerability.

Official or primary support. ClickHouse URL function and permissions. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S10 Apply resource admission before expensive decoding

Independent origin: R1-03 · Classification: conditional risk / implementation or acceptance gate

Source locations. I5, MD 995; REC-04, MD 1085 and 1095; prototype, MD 1147. DOCX P1108–P1110, P1196–P1198, P1209, P1250; pp. 26, 29–30, 32.

Spec anchor. “bound memory/queues and avoid retry storms”

Counterexample and impact. A bounded postdecode queue admits 100 batches, while 200 concurrent transport requests decompress and allocate objects before acquiring permits. Per-message limits and queue limits still allow multiplicative prequeue memory/CPU exhaustion.

Proposed fix. Budget connections/bodies before authentication and tenant decode work as early as identity allows. Limit compressed/decompressed bytes, decode concurrency and structural expansion, accounting for copies/redaction/fan-out. Exact values remain workload decisions.

Acceptance evidence. Flood every adapter with concurrent legal maximum messages, compressible input, many small fields, slow bodies and unauthorized requests. Check preadmission allocation/concurrency and peer progress, not only queue depth.

Calibration and gate. Bounded memory is already required and payload limits are deferred. This is an enforcement-placement and test refinement; implementations with correct transport admission may already satisfy it.

Official or primary support. OTLP request-size and overload semantics · Tonic decoding message limits. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S11 Include IaC artifacts in the credential lifecycle

Independent origin: R2-04 · Classification: conditional risk / implementation or acceptance gate

Source locations. §3.1, MD 180; §4.3, MD 251–257; §8.2, MD 400; TEST-010, MD 628. DOCX P0242, P0315–P0318, P0432, P0746–P0748; pp. 5, 7, 10, 16.

Spec anchor. “Manage platform resources as code”

Counterexample and impact. A provider marks a datasource password sensitive and never returns it from the platform API, but still persists its configured value in state or saved plans. Platform credential privacy and a successful IaC smoke test do not protect those copies.

Proposed fix. Offer a supported secret-reference or version-compatible write-only/ephemeral path. Define creation, rotation, read/import and drift semantics without exposing values, and document any client/version path that necessarily stores them. Masking alone must not be described as persistence avoidance.

Acceptance evidence. Create, rotate, refresh, import and destroy credential-bearing resources. Search plans/state/logs/errors/support exports for a unique canary; ensure the declared secret-free route stays clean and produces stable plans.

Calibration and gate. Terraform/OpenTofu capability differences remain implementation choices. The recommendation is a tested safe lifecycle, not mandatory adoption of one framework or version.

Official or primary support. Terraform sensitive values versus state persistence · Provider write-only arguments. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P3 S12 Test headless installation from empty identity state

Independent origin: R2-05 · Classification: conditional risk / implementation or acceptance gate

Source locations. §9.1, MD 491; TEST-001/010, MD 619 and 628; §22.5, MD 1055. DOCX P0494, P0719–P0721, P0746–P0748, P1161; pp. 12, 15–16, 28.

Spec anchor. “Default deny where valid permissions cannot be established”

Counterexample and impact. CI precreates an administrator directly in storage and passes headless tests. A real clean installation has no trusted principal to create its first owner; a later unauthenticated first-admin endpoint creates a takeover race.

Proposed fix. Document installation/operator possession, atomic first-owner establishment, idempotent/concurrent initialization and consumed bootstrap authority. Test a supported recovery path separately. An OS-admin-controlled local initializer or securely preseeded configuration is valid; no specific identity product is required.

Acceptance evidence. Install from clean storage without UI, hosted service or direct database editing. Establish authority and constrained accounts. Unauthorized competing setup, credential reuse, restart and recovery must obey the documented boundary.

Calibration and gate. Original R2 P2 was lowered to P3: headless provisioning is already required; this is a stronger TEST-001 fixture. Default deny and secure bootstrap are compatible, so there is no architectural contradiction.

Official or primary support. Vault explicit initialization as a reference lifecycle. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P2 S13 Prevent benchmark stalls from silently reducing offered demand

Independent origin: R1-04 · Classification: conditional risk / implementation or acceptance gate

Source locations. §23.6, MD 1127–1131; §24.2, MD 1151–1155. DOCX P1240–P1242, P1252–P1254; pp. 31–32.

Spec anchor. “Report distributions, run-to-run variability, errors and raw configuration/results.”

Counterexample and impact. A response-paced generator sends fewer queries when replay stalls the server. P99 of completed responses looks acceptable under reduced contention. An arrival generator can likewise omit unsent iterations or timeouts from its latency summary.

Proposed fix. Predeclare open/closed arrival semantics and justify them for the workload. Preserve scheduled send times; report scheduled/sent/completed/rejected/timed-out/unsent counts and client queueing separately from service time. Define generator overload and timeout treatment before pass/fail.

Acceptance evidence. Inject a known multi-second stall. The harness must expose scheduled demand and its latency/loss impact, rather than hiding it through rate collapse or omitted work.

Calibration and gate. Both workload models can be valid. The spec already demands offered rates, errors and repeated trials; this completes measurement semantics before comparisons settle language/storage decisions.

Official or primary support. k6 open versus closed models · k6 dropped iterations. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

P3 S14 Measure deployment memory pressure beyond process RSS

Independent origin: R1-05 · Classification: conditional risk / implementation or acceptance gate

Source locations. §23.6, MD 1127; §24.2, MD 1149–1153; §22.5, MD 1066. DOCX P1240, P1251–P1253, P1175–P1176; pp. 29, 31–32.

Spec anchor. “CPU, RSS/peak memory, allocations/GC where applicable, disk/network I/O”

Counterexample and impact. Heap/RSS stays low while WAL/compaction builds charged dirty file cache and kernel/socket memory in a constrained Linux deployment. Reclaim, writeback stalls or OOM can harm fresh ingest while process-only graphs suggest comfortable headroom.

Proposed fix. Define scope across gateway, workers and shared dependencies. For Linux container profiles record cgroup total/peak and anon/file/kernel memory, memory events, swap/pressure and writeback under equivalent quotas, alongside RSS/allocator metrics. Use appropriate equivalents on other platforms.

Acceptance evidence. Combine constrained-memory replay, compaction and throttled storage. Correlate charged memory/pressure with fresh ingest and alert tails; disclose shared dependency costs and OOM/reclaim failure.

Calibration and gate. Original R1 P2 was lowered to P3: peak memory and I/O are already requested and could reasonably include these measures. Escalate if an actual RSS-only acceptance plan is proposed. This is a deployment-specific benchmark clarification, not an argument against Rust or a new required platform.

Official or primary support. Linux cgroup v2 memory and writeback accounting. The counterexample and recommended contract are reviewer inferences from these sources and the specification, not external claims that project code is vulnerable.

Contradictions, risks and preferences

No demonstrated irreconcilable contradiction. In particular, immutable finalized history explicitly permits deletion/redaction at MD 919; source privacy includes spools/WALs at MD 995; at-least-once/idempotent publication is not an exactly-once claim at MD 927–935; and fresh/backlog scheduling is already conditional on ordering compatibility at MD 1091. These are not new defects. The diagram’s stacked planes are explicitly logical, not a mandatory synchronous dependency chain.

Risks: the retained findings identify narrower contract or acceptance gaps inside those coherent responsibilities. S01–S02 clarify how trust and permissions compose. The others principally refine already-deferred implementation and validation gates. S05 does not prove a prohibition on GenAI log events; S06 does not prove the spec requires a frozen snapshot; S07 does not claim it mandates a counter; S12 does not claim default deny contradicts bootstrap.

Preferences: Rust versus Go, exact engines, queue products, executor choice, policy engine, capture defaults and numerical SLOs remain as classified in the spec. No reviewed source establishes a universal language winner. The 25× recovery illustration at MD 1112 is mathematically sound under its explicit constant-rate assumptions; the owner’s 24h/1h/16-thread report remains contextual, unverified operational experience. None of the findings requires a fifth plane, one database, a mandatory cloud service or a second design conversation.

Recommended implementation gates
